## Status and purpose

The detailed case sections below define the test plan; the execution checkpoint above records current outcomes. Every case starts **NOT RUN**. Promote a case to PASS or FAIL only with direct evidence; use BLOCKED for a missing dependency or authorization. Record a useful partial outcome without calling the entire case passed. Test priority is not defect severity.

Two tracks run against the same journey:

- **Beginner UX:** approach Datadog and APM with no assumed product vocabulary. Record the first path taken before consulting documentation. Evaluate whether the interface explains what to do next.
- **Deep functional QA:** challenge identity, configuration scope, source revision, lifecycle, permissions, stale state, and recovery. Validate the actual result rather than a success toast.

Do not operate an existing production service, real customer data, or a shared integration to manufacture a failure. Keep external mutations within the user's authorized scope. Persistent-access changes, credentials, account permission changes, and widening repository grants require their applicable approval. A BLOCKED test is preferable to an unsafe experiment. Read-only inspection, form validation, and navigation may continue independently.

## Fixture and known oracle

The audit uses a synthetic Python quote service with the oracle below. Runtime telemetry and debugger capture have not yet been verified at this checkpoint.

- Python function: `pricing.calculate_quote`; file: `pricing.py`; intended capture line: **17**, the start of the return expression. Verify actual deployed line numbers before use.
- Line 13 intentionally uses `quantity > 3`; do not fix the baseline before testing.
- Synthetic traffic: `python traffic.py --count 180`, approximately one request every 1.1 seconds, cycles quantities 2, 3, and 4. This script targets loopback only. Run it on the machine hosting the fixture.
- Quantity 2 oracle: subtotal 2400, eligibility false, discount 0, total 2400.
- Quantity 3 oracle: subtotal 3600, eligibility false, discount 0, total 3600. Intended business total would be 3240.
- Quantity 4 oracle: subtotal 4800, eligibility true, discount 480, total 4320.
- Numeric and Boolean locals avoid needing to relax redaction. Default sample execution sends no Datadog data. An instrumented deployment is a separate prerequisite, not established by the existence of these files.
- Use dedicated test service/environment labels and record their exact values. Verify service, environment, version, repository, deployed commit, SDK version, Agent version, process identity, and test clock before attribution.

For Source Code Integration, use synthetic repositories **A** and **B**, both private, with no real secrets or personal data. A contains the fixture. B is never granted to the tested integration and has a unique numeric/source marker. Inventory other GitHub installations, upload paths, or public mirrors that could already expose B. Do not infer a leak from public code or a pre-existing alternate grant.

## Gates and evidence conventions

| Gate | Prerequisite |
|---|---|
| G0 | Signed-in browser in the intended Datadog organization; read-only navigation/form cancellation available. |
| G1 | Authorized synthetic runtime, healthy Agent/SDK/remote configuration/log forwarding, and permission to create/disable test logpoints. |
| G2 | Approved integration limited to repo A, verified A commit mapping; B remains ungranted. |
| G3 | Approved sandbox permission/integration changes plus independent test identities. No modification of the auditor's sole admin account. |
| G4 | Approved additional fixture/deployment variants, commits, restarts, or controlled failure injection. |

Evidence abbreviations in the matrix:

- **V:** continuous screen recording plus timestamped screenshot at the decisive state; include URL, product, selected service/environment/version, and visible status. Exclude tokens, keys, private account settings, and unrelated data.
- **I:** entity identity: session/logpoint ID, exact repository/commit/path/line, matching deployment tag, and test case ID.
- **T:** bounded traffic ledger and event execution/capture timestamps. A late ingestion timestamp does not prove a late capture.
- **R:** independent reload/new tab/read-only state check, not only a toast or optimistic UI.
- **A:** access evidence: exact test identity/role, effective repository grant, requested target, and denial/result. Do not record credentials.
- **H:** fixture health before/after, HTTP responses, process/Agent observations as available. Never collect a secret-bearing whole environment dump.

For every case capture: test ID, UTC start/end, build/site/browser, gate status, actual steps, expected result, actual result, PASS/FAIL/BLOCKED/INCONCLUSIVE, direct evidence references, reproducibility, severity if a defect is observed, and cleanup verification. Network or console details are optional if the browser's authorized tooling supports them; do not invent them.

## Contract anchors and cautions

These official references were checked on 2026-10-08. Actual site/runtime and UI remain authoritative for this audit; documentation may differ by rollout. Search results can combine language tabs, so verify the selected language before quoting a version.

1. [Live Debugger](https://docs.datadoghq.com/tracing/live_debugger/): manual sessions can operate without source linking; activation can take minutes; target identity is immutable after logpoint creation. Variable capture is limited; redaction and independent log retention matter. Use this as the contract for F02/F11/F15/F16, not as evidence they passed.
2. [Bits Live Debugger](https://docs.datadoghq.com/tracing/live_debugger/bits-live-debugger/): requires connected source, product availability, and appropriate access. Documented expiry range is 10 minutes to two days, default 60 minutes; verify the actual displayed settings before scheduling F11.
3. [Source Code Management Providers](https://docs.datadoghq.com/source_code/source-code-management/): repository contents may be retained in a cache for up to seven days. This is why S03 and S10 isolate never-granted and never-fetched content.
4. [Python source mapping](https://docs.datadoghq.com/source_code/service-mapping/python/): `DD_GIT_REPOSITORY_URL` and `DD_GIT_COMMIT_SHA` identify the repository and deployed commit. Do not substitute current branch HEAD for the deployed SHA.
5. [Expression language](https://docs.datadoghq.com/tracing/trace_collection/dynamic_instrumentation/expression-language/): conditions use its own grammar; `isDefined` exists; arbitrary method calls are unsupported; method contextual variables have narrower scope than line locals.
6. [Role permissions](https://docs.datadoghq.com/account_management/rbac/permissions/) and [debugger MCP permission notes](https://docs.datadoghq.com/mcp_server/tools/): Live Debugger read/write/redaction permissions differ, and snapshot access depends on Logs permissions. Verify effective access with real test identities.
7. [Sensitive-data scrubbing](https://docs.datadoghq.com/tracing/trace_collection/dynamic_instrumentation/sensitive-data-scrubbing/): identifier/type-based scrubbing occurs before upload; Sensitive Data Scanner is post-upload. Fake canaries only; do not equate later masking with never transmitting a value.
8. [GitHub integration](https://docs.datadoghq.com/integrations/github/) and [source features](https://docs.datadoghq.com/source_code/features/): use actual installation scope and provider target as evidence. Avoid assuming every feature needs identical permissions.
